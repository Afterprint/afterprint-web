**Status:** Authoritative build source of truth

---

## 1. Product definition

Afterprint helps authorized investigators, forensic teams, lawyers, regulators, insurers, and reviewers organize fragmented evidence into an auditable picture of what the evidence supports.

It ingests items such as:
- CCTV/video;
- photos;
- audio;
- witness statements;
- reports;
- GPS/location records lawfully supplied;
- vehicle/device telemetry;
- forensic/medical reports;
- documents;
- sensor logs.

AI synchronizes events, extracts entities, links evidence, flags contradictions, supports natural-language search, and drafts a reconstruction.

Afterprint **does not decide guilt**, perform autonomous accusation, or turn model confidence into legal truth.

Stellar acts as a trust stamp for evidence hashes, custody transfers, attestations, and selected access proofs. Raw evidence stays encrypted off-chain.

## 2. Non-negotiable evidence model

Every AI conclusion belongs to exactly one category:

1. `VERIFIED_FACT` — directly supported by an authenticated evidence source.
2. `CORROBORATED_CLAIM` — supported by multiple independent sources.
3. `INFERENCE` — interpretation/hypothesis, never presented as fact.
4. `CONFLICT` — evidence disagrees.
5. `UNKNOWN` — insufficient evidence.

The UI, APIs, exports, and reports must preserve these labels.

## 3. Safety/legal product invariants

- no guilt/innocence score;
- no "suspect likelihood" score;
- no automatic lie detection;
- no hidden face recognition/biometric identification in MVP;
- no invented missing events;
- no AI-generated "fact" without source evidence;
- every transformation creates a derived artifact; originals are immutable;
- defense/exculpatory evidence uses the same retrieval standards as inculpatory evidence;
- human review is required before an AI draft becomes an official reconstruction/report;
- chain of custody is append-only;
- raw case evidence is never stored on Stellar.

## Repository interaction rules

1. `*-web` talks only to `*-api` for authoritative product operations.
2. `*-web` never receives database, object-storage, AI-provider, Redis, or Stellar signing secrets.
3. `*-api` is the system-of-record and authorization boundary.
4. `*-ai` never decides whether a user is allowed to see data. It accepts only already-authorized jobs from the API.
5. `*-contracts` never stores the product's private domain data. Only opaque identifiers, hashes, permissions/attestations, and minimal public state go on-chain.
6. Cross-repo contracts are versioned. Breaking a request/response schema without updating consumers is a failed change.
7. All asynchronous work is idempotent. Every job receives an idempotency key.
8. The API owns database migrations. The AI repo owns AI-index/evaluation migrations. The contracts repo owns contract upgrades.
9. All development/demo fixtures use synthetic data.
10. No contributor needs production secrets or real private data to complete a Wave issue.

## 8. Immutable ingest flow

1. Authorized user requests upload.
2. API creates evidence item and upload session.
3. Client uploads directly to private object storage using short-lived signed URL.
4. Client finalizes upload.
5. API streams/re-reads object to compute SHA-256; do not trust client hash alone.
6. API stores immutable `EvidenceVersion`.
7. Original bucket object versioning is enabled.
8. API creates `COLLECTED/IMPORTED` custody event.
9. Queue evidence processing.
10. Queue Stellar evidence anchor.
11. AI processes a signed read-only copy/URL.
12. All AI/media outputs return as derived artifacts with their own hashes.

Never edit an original file in place.

### Audio

### Images

### Documents

## 13. Timeline model

Time is never a single unquestioned timestamp.

Each event stores:
- candidate start/end;
- precision (`EXACT`, `MINUTE`, `APPROXIMATE`, `RANGE`, `UNKNOWN`);
- source;
- basis (`DEVICE_METADATA`, `VISIBLE_CLOCK`, `STATEMENT`, `SYSTEM_LOG`, `INFERRED`);
- timezone;
- clock-drift adjustment if reviewed;
- confidence for model extraction, not "truth."

Synchronization creates relationships but preserves original time claims.

## 14. Conflict engine

Conflict types:
- timestamp conflict;
- identity/label conflict;
- location conflict;
- sequence conflict;
- statement-vs-record conflict;
- duplicate/inconsistent artifact;
- integrity/hash conflict.

Rules:
- a conflict does not imply deception;
- show sources on both sides;
- human can mark `REVIEWED`, `RESOLVED`, `EXPECTED`, or `OPEN`;
- original extracted conflict record remains auditable.

## 15. Query system

Example: "Show every evidence item that places Vehicle X in the area between 20:50 and 21:20."

Pipeline:
1. API verifies case membership/permission.
2. Parse query into entities/time/evidence filters.
3. Retrieve structured graph/timeline data.
4. Retrieve supporting source spans/frames.
5. Generate atomic claims.
6. Assign claim category.
7. Verify citations.
8. Return evidence refs and exact location (page/frame/time/span).
9. If support is ambiguous, use `CONFLICT` or `UNKNOWN`.

No answer may convert an `INFERENCE` into `VERIFIED_FACT`.

## 16. Reconstruction engine

Output structure:

```json
{
  "verifiedFacts": [],
  "corroboratedClaims": [],
  "conflicts": [],
  "unknownPeriods": [],
  "hypotheses": [],
  "timeline": [],
  "sourceManifest": []
}
```

A reconstruction draft is not an official report until a human reviewer explicitly finalizes it.

Finalized report stores:
- exact evidence version IDs;
- derived artifact IDs;
- reviewed claim IDs/categories;
- report hash;
- reviewer;
- optional Stellar attestation.

## 17. AI system policy

- Organize evidence; do not determine guilt.
- Never accuse a person based on model inference.
- Every factual claim must cite evidence.
- Clearly label inference and uncertainty.
- Never call a contradiction a lie.
- Do not invent events to fill gaps.
- Do not use facial recognition/biometric identification in MVP.
- Present exculpatory/contradictory evidence using the same retrieval threshold.
- Model confidence describes model confidence, not legal probability.
- Human review controls final reports.

## 18. Stellar contracts

### Privacy
On-chain fields use opaque refs/hashes. No case title, person name, witness statement, evidence content, or location details.

### `CaseRegistry`
- register opaque case ref, controller org/address, metadata hash

### `EvidenceAnchorRegistry`
- `anchor(evidence_version_ref, manifest_hash, submitter_ref)`
- immutable per version
- `get(evidence_version_ref)`

### `CustodyRegistry`
- `transfer(event_ref, evidence_version_ref, from_ref, to_ref, event_hash, timestamp)`
- authorization requires expected custodian/controller
- append-only

### `AttestationRegistry`
- `attest(attestation_ref, subject_ref, statement_hash, issuer_ref)`
- immutable statement hash

### `AccessGrantRegistry`
Optional cross-organization sharing proof:
- grant opaque access policy hash;
- revoke;
- no readable case/evidence scope on-chain.

## 19. Chain-of-custody hash chain

Application DB custody events should also form a hash chain:

`event_hash = SHA256(previous_event_hash || canonical_event_json)`

Store:
- `previous_hash`
- `event_hash`

Periodically/batch anchor custody head hash to Stellar. This reduces on-chain writes while preserving tamper evidence.
